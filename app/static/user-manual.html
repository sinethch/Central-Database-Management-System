1. Getting started

DBOps is a browser-based control plane. It keeps its registry and snapshot metadata locally and connects to configured database targets for monitoring and backup operations.

  1. Sign in with your username and password. Microsoft Authenticator is required only for accounts that have MFA enabled. For an MFA-enabled account, use the QR code or setup key provided by an administrator to configure Microsoft Authenticator, then enter the six-digit code when prompted.
  2. Use the target cards below the hero to choose the active database. Click a card, drag the carousel, use its arrow buttons, or focus it and press the left/right arrow keys. Dashboard metrics use the selected target; manual snapshots require a selected PostgreSQL target, and the backup schedule has its own database selection.
  3. Use Add database instance to register a database, or Add Server in Database Servers to register a remote Linux Docker host.
For MFA-enabled accounts, keep the Authenticator setup key safe. Keep AUTH_TOTP_ENCRYPTION_KEY stable; changing it can prevent verification of stored authenticator seeds.
Before production use: configure unique private API and encryption keys in .env, restrict access to the control plane, and protect the local backup directory. Never paste connection strings or credentials into chat, screenshots, or logs.

2. Navigation and sections

The navigation links move between dedicated workspaces. Each workspace is a full page (/console, /overview, /backups, /restore, /restored-databases, /storage, /activity) and shows only the controls and data for that task. Choose the active target in Console; Overview, Backups, and Storage use that selection. Restore has its own source-database selector.

3. Registering and removing database targets

Add a database

  1. Click Add database instance.
  2. Enter a display label and connection URL. Supported schemes include postgresql://, mongodb://, mongodb+srv://, mysql://, and redis://; the engine is detected from the URL and can be reviewed in the form.
  3. Click Test Connection to check connectivity, then Add Database.
  4. Select its target pill to view its dashboard.

The connection test and monitoring queries are intended to read telemetry. The account still needs enough permissions to read the metrics being displayed. Store connection credentials securely and use a monitoring account with limited privileges.

Remove a target from monitoring

Select the target and click Unregister. This removes its entry from the app registry. It does not issue a database drop, modify records, or delete the database.

4. Dashboard and health

The Overview workspace summarizes connection health and available database metrics. Depending on the engine and permissions, it can show connections, buffer-cache hit ratio, storage, query activity, slow operations, table sizes, and lock contention. Database Servers cards show host health such as Docker version, memory, disk use, load average, and DBOps container counts.

  • Live refresh: dashboard data refreshes automatically about every eight seconds. Use the pause control in the header to stop or resume it; use Refresh to fetch metrics immediately.
  • Server health: refreshes periodically while the page is visible; the server card also offers a manual health refresh.
  • Alerts: the header opens Telegram notification settings. Configure the bot, chat, delivery options, and event subscriptions, then save; use Send Test to check delivery.
  • Kill: where shown for a long-running query, this cancels that operation. It is an active database action; use it only when you intend to interrupt the query.

5. Migration history

The Recent Migrations card and Migration History table provide read-only discovery of recognized PostgreSQL migration ledgers for the selected target. Use Refresh history to check again. DBOps does not apply migrations or change schema/data through this feature.

If enabled in Telegram event subscriptions, New migration detected alerts when a new record appears in a recognized ledger. DBOps checks periodically; the initial scan establishes a baseline and does not alert on records that were already present. A ledger the app does not recognize cannot be reported by this feature.

6. Remote servers

Register a host

  1. On the control-plane machine, connect to the host with terminal SSH and verify its host key. The app requires the matching entry in its configured known_hosts file.
  2. Set SSH_KNOWN_HOSTS_PATH so Docker mounts the trusted file into the app. Unknown or changed host keys are rejected before password authentication.
  3. Set SERVER_CREDENTIAL_ENCRYPTION_KEY to a unique random secret of at least 32 characters. Keep it stable; the app needs it to decrypt registered SSH passwords.
  4. In Database Servers → Add Server, enter the label, IP, SSH port, account, password, and absolute Linux database and snapshot paths.
  5. The path parents must already exist and the SSH account must have the required permissions. The paths may be identical or overlap. Registration checks paths and Docker availability over SSH; it does not create remote files.

Health, provisioning, and removal

Health checks use read-only SSH commands. Create PostgreSQL Container adds a new container and new files below the configured database path; choose an unused host port. It does not repurpose existing containers or database directories. Remove Server removes only the server registration from this app. Containers, files, remote snapshots, and separately registered database targets remain on the host or in the app.

The app rejects path traversal and symlinked path components. Use paths dedicated to DBOps and grant the SSH account only the needed filesystem and Docker access.

7. Taking a manual snapshot

Dashboard monitoring supports multiple database engines, but snapshot and restore operations are currently for PostgreSQL targets.

  1. First select a PostgreSQL target to back up.
  2. Click Take Snapshot from the hero or Backups section. The dialog shows the currently selected target.
  3. Choose an archive format, compression, and optional encryption; add a description if useful.
  4. Optionally check one or more registered remote servers to copy the completed archive to their configured snapshot directories.
  5. Click Start Snapshot. Review the Backups table for status, ID, size, and checksum-related actions.
  • Custom Archive (.dump): recommended for PostgreSQL; restored with pg_restore.
  • Plain SQL (.sql / .sql.gz): script format, restored with psql.
  • Compression: reduces storage use. Custom archives use pg_dump compression; plain scripts use gzip.
  • Encryption: optional archive encryption. Set a unique BACKUP_ENCRYPTION_KEY before relying on this option and keep a protected copy. Losing or changing the key prevents decryption. The checkbox is labeled “AES-256” in the current UI; confirm the encryption algorithm meets your organization's requirements before depending on a particular strength.
  • Remote copies: are transferred after the local archive completes. The app verifies SHA-256 before recording a copy as available. A copy failure does not remove the local snapshot.

Manual snapshots are always stored in the configured local backup directory (default ./backups); this dialog offers optional remote-server copies. Mounted repositories can be selected as destinations in the automated schedule.

8. Backup schedule

  1. Click Backup Schedule.
  2. Choose Every day, Every week, or Every month.
  3. Choose the time in UTC. The preview also shows the equivalent Sri Lanka time (UTC+5:30). Weekly schedules include the Sri Lankan weekday if the date changes across time zones.
  4. For a weekly schedule, choose a weekday. For monthly, choose day 1–28 so it exists in every month.
  5. Set status to Active and click Save Schedule. Choose Disabled to pause scheduled backups.

Select the PostgreSQL database to back up and optionally select mounted repositories and/or registered remote servers as additional destinations. Every scheduled snapshot is saved locally, and selected destinations receive copies that are checksum-verified. The schedule is independent of the active dashboard target. The default schedule is daily at 02:00 UTC (07:30 Sri Lanka time); the dialog displays the next run in UTC and Sri Lanka time. If an existing custom schedule is loaded, you can keep it using the current schedule option.

Local snapshots older than the configured retention period are removed by the app’s retention cleanup. The default is 14 days. This applies to local archive files; it does not remove remote server copies.

9. Verify and manage snapshots

In the Backups table, use Verify to check archive integrity without restoring it. A valid archive is not a complete disaster-recovery test; periodically restore a snapshot to a disposable target and confirm the resulting database works.

Use Download to retrieve an archive from local app storage. Keep at least one protected copy outside the machine hosting the control plane if that machine is part of your failure scenario. Remote copies use the registered server’s snapshot path and are not removed when that server is unregistered.

10. Restoring a snapshot and restored databases

New database: the snapshot is loaded into a fresh PostgreSQL database, leaving existing databases unchanged. Existing database: the public schema in the selected database is dropped and recreated before restoring the snapshot. This removes existing objects in that schema, including objects absent from the snapshot. The reset and restore run in one transaction, so a restore error rolls them back. This operation may hold locks; use it only when replacing that schema is intended.
  1. Choose a completed snapshot with Restore in the Backups table, or click New Restore to choose a snapshot.
  2. Select the local or mounted copy, or a registered remote server with a checksum-verified copy. Remote copies support new-database restores only.
  3. Choose a registered PostgreSQL destination. Create a separate new database (recommended) and enter an unused name, or explicitly choose to write into an existing registered database.
  4. Type the confirmation phrase displayed in the dialog: RESTORE for a new database or RESTORE EXISTING for an existing database.
  5. Review the restore plan and click Restore Now. Follow status and logs in Restore Center. The source archive is checksum-verified and staged locally before restore.

Snapshot exports omit owner and privilege settings, so configure roles, grants, and ownership separately as needed.

Restored Databases

The Restored DBs section lists clone restores. If a restored database is not yet in Targets, select Add to Targets to monitor it. Administrators can copy a full connection URL from this section; treat the URL as a credential. It uses the app’s Docker network name; users connecting from outside Docker may need a reachable host name or IP and the published PostgreSQL port. Remove from Targets removes its monitoring entry only; it does not delete the database or its data.

11. Users and multi-factor authentication

The Users control is available to administrators. Use it to create or remove sign-in accounts. New usernames must be 2–32 characters using letters, numbers, underscores, periods, or hyphens; temporary passwords must be at least 12 characters.

MFA is optional per account. When creating a user, select Enable Microsoft Authenticator (MFA) only if that account should require MFA. If selected, securely provide the displayed QR code or manual setup key to the user for enrollment. If it is not selected, that user signs in with username and password and is not prompted for an Authenticator code.

Share MFA setup details and temporary passwords securely. Never include them in screenshots, chat, or support logs.

12. Activity and shortcuts

The Activity section shows recent operations such as snapshots, pings, verifications, and target switches, grouped into operator branches. Use Clear Log only when you intend to clear the activity feed. The header’s command palette searches actions and registered databases; open it with Ctrl+K (or ⌘+K on macOS), then select a result. Use the theme control to switch between light and dark appearance.

13. Safety boundaries and credentials

  • Registering a database adds a connection record to the app; it does not copy the database.
  • The Migration History panel and migration alert monitor check recognized PostgreSQL migration ledger tables with read-only SELECT queries. They never run migrations or change schema/data. Migration alerts identify new records in recognized ledgers; an unrecognized or external ledger cannot be monitored by this feature.
  • Monitoring and connectivity checks query metrics; the explicit Kill action cancels a running query.
  • Taking a snapshot reads from the source database. A new-database restore creates a separate database. An existing-database restore writes the selected snapshot's objects and data into the chosen database; use the explicit confirmation and understand it can affect application workload.
  • Remote server registration does not create remote files. Provisioning creates a new DBOps container and new files below the configured database path. Snapshot replication creates new files below the configured snapshot path.
  • Removing a server or unregistering a database removes its app registration only. Neither operation deletes remote data or stops a container.
  • Keep .env, database URLs, SSH passwords, SSH host keys, and encryption keys private. Back up the encryption keys separately from encrypted archives.

14. Troubleshooting

  • Connection test or monitoring fails: check the connection URL, network/firewall, database availability, and account permissions.
  • An account receives an unexpected MFA prompt: ask an administrator to confirm whether MFA was enabled for that account. MFA is not required for accounts created without the option selected.
  • SSH says host not found in known_hosts: verify the host key with terminal SSH on the control-plane machine, then ensure the exact trusted entry is present in the file mounted at SSH_KNOWN_HOSTS_PATH. Do not bypass host-key checks.
  • Credential encryption key error: set a unique SERVER_CREDENTIAL_ENCRYPTION_KEY of at least 32 characters, then restart the app.
  • Remote path error: use an absolute Linux path, confirm its parents already exist, and confirm there are no symlinked path components.
  • Remote snapshot missing: verify that the copy completed and is listed as checksum-verified on the selected server. A local snapshot alone does not imply that a remote copy exists.
  • Restore fails because the name exists: choose a different unused name for a new-database restore. For an existing-database restore, check the selected destination and the confirmation phrase before trying again.

Avoid including passwords, keys, or unredacted connection URLs in support messages.
